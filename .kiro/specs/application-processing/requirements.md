# Requirements Document

## Introduction

The Application Processing feature provides a generic, reusable capability for capturing the basic information required to process a finance (loan) application and for generating an Amortization Schedule derived from the application's Finance Amount and Interest Rate (IRR). The feature gives operational personnel a single Application Processing Form that records the core terms of an application (Line of Business, Customer, Product, Branch, Scheme, finance amount, interest rate, tenure, repayment frequency, disbursement date, and processing charges) and, from those terms, computes a reducing-balance repayment schedule showing the per-installment split of principal and interest, the opening and closing outstanding balances, and the summary totals. Reference and classification fields on the form (Line of Business, Customer, Branch, Product, Scheme, and any other lookup-backed classification values) are populated from the platform's existing reference and lookup mechanisms and are selected rather than typed as free-form text.

The stakeholder (acting as experienced financial personnel) has explicitly requested a **generic** processing form. Real-world finance terms vary by customer segment, product, and regulatory treatment; those variations are deliberately out of scope for this iteration. This feature establishes a standardized baseline that later customer-specific or product-specific processing rules can extend. The amortization computation is the heart of the feature: it is a deterministic financial calculation, so its correctness properties (the principal portions summing exactly to the Finance Amount, every balance being non-negative, the schedule closing to a zero balance) are specified precisely so they can be verified by example and by property-based tests.

Finnova is an India-only, English-only platform. All monetary amounts are expressed in Indian Rupees (INR), all interest rates are per-annum percentages following Indian financial convention, and all user-facing text is English. There are no bilingual fields, no non-English sample data, and no right-to-left rendering.

This feature follows the platform's layered CQRS conventions (ASP.NET Core Web API, MediatR, FluentValidation, EF Core + SQL Server, generic `IRepository<T>` + `RepositoryBase<T>`, record-based contracts with `.ToResponse()` mappers, `PaginatedResponse<T>`) and is hosted behind the `Finnova.ApiGateway` YARP reverse proxy. The user-facing Application Processing screen is implemented in the separate Finnova-UI repository (React + TypeScript + Material UI + Vite). This spec covers both the backend API and the frontend screen.

This document captures the requirements for a generic Application Processing Form. Where the stakeholder left a decision open ("I trust you as a Financial Personnel"), the chosen financial convention is recorded explicitly as an **Assumption** within the relevant requirement so it can be confirmed during review.

### Dependencies and Cross-Cutting Assumptions

- **Assumption (Host placement):** The Application Processing API is placed in a backend service host reached through the gateway. Whether it is hosted in `Finnova.AccountsService` (the service that already owns account and transaction concerns), `Finnova.SystemAdminService`, or a dedicated host is a host-placement decision proposed for confirmation during design. The Application Processing concern is operational (not master-data), so `Finnova.AccountsService` is the proposed host.
- **Assumption (Authentication dependency):** The chosen host already configures JWT Bearer authentication, and the UI shared axios instance injects the JWT Bearer token from `localStorage('finnova_token')`. This feature reuses that scheme. Token issuance (login) ownership is external to this feature.
- **Assumption (Applicant / Customer reference):** The Application Processing Form references the applicant as a Customer selected from the existing Customer Master, by the Customer's identifier/code, rather than embedding full customer data or capturing a free-form string. The selected Customer is validated for existence (the reference must be resolvable against the Customer Master). Whether existence is enforced as a strict database foreign-key relationship or as presence-only validation (the reference resolves to an active Customer at submission time) is proposed for confirmation during design; in either case the field is a selection sourced from the Customer reference/search source, not free text.
- **Assumption (Reference and lookup consumption):** Application Processing CONSUMES the platform's existing reference and lookup mechanisms and does not create, manage, or seed any lookup values, Line of Business records, Customer records, or Branch records. Line of Business is sourced from the existing active LOB reference list exposed as `LineOfBusinessRefResponse(Id, LobName, LobDescription)`. Customer is sourced from the existing Customer Master reference/search source. Branch is sourced from the existing active Branch Master/reference source; the exact Branch Master endpoint and response contract are not established in this requirements document, and Application Processing only consumes the active branch options. Product and Scheme are sourced from the shared Lookup catalog via the Lookup dropdown API `GET .../lookup/dropdown?module={module}&type={type}`, which returns active `LookupDropdownItemResponse(Code, Label)` items. The proposed Lookup Module is `ApplicationProcessing` (alternative `Origination`), and Product and Scheme are proposed lookup Types; the exact module and type names are confirmable assumptions. Any additional status/category classification fields also consume the shared Lookup catalog. Admin management of lookup values, Line of Business records, Customer records, and Branch Master records is owned by separate features and is OUT OF SCOPE here. Repayment Frequency is NOT a lookup-backed field: it remains a fixed enumerated set (Monthly, Quarterly, Half-Yearly, Annual) because the amortization math (periods per year) depends on the exact enumerated values, so it is intentionally not sourced from the Lookup catalog.
- **Assumption (Currency):** All monetary amounts are in INR and are stored and computed with two decimal places (paise precision). Rounding of computed interest and principal uses round-half-up to the nearest paisa (0.01 INR).
- **Assumption (Interest model):** The generic schedule uses the reducing-balance (declining-balance) method with equal periodic installments (EMI). IRR is interpreted as a nominal per-annum interest rate; the periodic rate is the annual rate divided by the number of periods per year. Flat-rate and other interest models are out of scope for this iteration and flagged for confirmation.
- **Note (Localization):** Each application and schedule carries single English display values; there are no bilingual fields, no non-English content, and no right-to-left rendering.

## Glossary

- **Application**: A single finance (loan) application record captured through the Application Processing Form, consisting of an Application Number, Line of Business, Customer, Product, Branch, Scheme, the finance terms (Finance Amount, IRR, Tenure, Repayment Frequency, Disbursement Date), optional Processing Charges, an Application Status, and audit timestamps.
- **Application Processing Form**: The Application Processing screen used by operational personnel to capture and process an Application (implemented in the Finnova-UI repository).
- **Application Number**: A human-readable identifier for an Application, unique across the Application Processing feature.
- **Customer**: An applicant on an Application, selected from the existing Customer Master and referenced on the Application by the Customer's identifier/code. The Application holds the Customer reference only (it does not embed full customer data); the reference must resolve to an existing active Customer. In the UI the Customer is chosen through a searchable selection (dropdown/autocomplete), not typed as a free-form string.
- **Line of Business (LOB)**: An existing master classification of finance business lines, held in the `lines_of_business` table and exposed as the active reference list `LineOfBusinessRefResponse(Id, LobName, LobDescription)`. An Application references an existing active Line of Business by its identifier, selected from this reference list; the feature consumes the list and does not create or manage Line of Business records.
- **Product**: A finance product selected on an Application from an active code/label item in the shared Lookup catalog. Product is represented by its lookup code and is selected through a dropdown; Product is not free-form text and Application Processing does not manage Product definitions.
- **Branch**: The active branch reference selected on an Application from the existing Branch Master/reference source. Branch is represented by its Branch Master identifier or code, is selected through a dropdown or searchable selection, and is not free-form text.
- **Branch Master**: The existing platform reference source that owns active branch records and exposes branch options for selection. Application Processing consumes active Branch Master items and does not create or manage branch records; the exact endpoint and response contract remain a confirmable assumption.
- **Scheme**: A finance scheme selected on an Application from an active code/label item in the shared Lookup catalog. Scheme is represented by its lookup code and is selected through a dropdown; Scheme is not free-form text and Application Processing does not manage Scheme definitions.
- **Lookup Dropdown**: A list of active code/label items sourced from the platform's shared Lookup catalog, fetched by a consuming module through the Lookup dropdown API `GET .../lookup/dropdown?module={module}&type={type}`, which returns `LookupDropdownItemResponse(Code, Label)` items to any authenticated caller. Application Processing consumes Lookup Dropdowns to populate Product, Scheme, and other lookup-backed classification fields and does not manage lookup values.
- **Reference/Lookup-backed field**: A form field whose permitted values come from an existing reference list or the shared Lookup catalog rather than being typed as free-form text. On the Application Processing Form these are Line of Business (from the `lines_of_business` reference list), Customer (from the Customer Master reference/search source), Branch (from the Branch Master/reference source), Product and Scheme (from the Lookup Dropdown API), and any other status/category classification fields (from the Lookup Dropdown API by module and type). Such fields are rendered as selection controls and are validated against the active reference items.
- **Finance Amount**: The principal amount of finance requested or sanctioned for the Application, expressed in INR. Also referred to as Principal.
- **IRR (Interest Rate)**: The nominal annual interest rate applied to the Application, expressed as a percentage per annum (for example, `12.5` for 12.5% per annum).
- **Tenure**: The number of equal repayment installments over which the Finance Amount is repaid.
- **Repayment Frequency**: The periodicity of installments. Supported values are Monthly, Quarterly, Half-Yearly, and Annual, corresponding to 12, 4, 2, and 1 periods per year respectively.
- **Disbursement Date**: The date from which the repayment schedule begins. The first installment falls one repayment period after the Disbursement Date.
- **Periodic Interest Rate**: The IRR converted to the repayment period, computed as the annual rate divided by the number of periods per year.
- **EMI (Equated Installment)**: The constant periodic repayment amount computed from the Finance Amount, the Periodic Interest Rate, and the Tenure using the reducing-balance annuity formula.
- **Amortization Schedule**: The ordered set of Installment Lines computed for an Application, showing per installment the opening balance, interest portion, principal portion, installment amount, and closing balance, together with summary totals.
- **Installment Line**: A single row of the Amortization Schedule for a given installment number.
- **Opening Balance**: The outstanding principal at the start of an installment period.
- **Closing Balance**: The outstanding principal at the end of an installment period (Opening Balance minus the principal portion of that installment).
- **Interest Portion**: The part of an installment that pays interest, computed as the Opening Balance multiplied by the Periodic Interest Rate.
- **Principal Portion**: The part of an installment that reduces the Opening Balance (installment amount minus Interest Portion).
- **Processing Charges**: An optional one-time fee associated with processing the Application, expressed in INR.
- **Application Status**: The lifecycle state of an Application. Supported states are Draft, Submitted, and Processed.
- **Paisa**: The smallest INR denomination used for rounding; one paisa is 0.01 INR.
- **System Administrator / Processing User**: An authenticated user authorized to capture and process Applications.
- **EARS**: Easy Approach to Requirements Syntax; structured patterns (Ubiquitous, Event-driven, State-driven, Unwanted-event, Optional-feature, Complex) used to write clear, testable requirements.
- **ApplicationProcessing_Service**: The backend service/API responsible for Application capture, processing, and Amortization Schedule generation.
- **ApplicationProcessing_UI**: The React-based Application Processing screen used by Processing Users (implemented in the Finnova-UI repository).

## Requirements

### Requirement 1: Capture Application Basic Information

**User Story:** As a Processing User, I want to capture the basic information of a finance application on a single form, so that the application's core terms are recorded for processing.

#### Acceptance Criteria

1. WHEN a Processing User submits a create request whose Line of Business, Customer, Product, Branch, Scheme, Finance Amount, IRR, Tenure, Repayment Frequency, and Disbursement Date all pass the validation rules in this requirement, THE ApplicationProcessing_Service SHALL persist a new Application and return the created record including a system-generated identifier, a generated Application Number unique across all Applications, and the resolved Application Status.
2. WHERE a create request omits Application Status, THE ApplicationProcessing_Service SHALL default the Application Status to Draft.
3. WHERE a create request omits Processing Charges, THE ApplicationProcessing_Service SHALL default Processing Charges to 0.00 INR.
4. IF a create request omits the Line of Business identifier, Customer reference, Product code, Branch reference, or Scheme code, or provides any of them as an empty or whitespace-only value, or omits Finance Amount, IRR, Tenure, Repayment Frequency, or Disbursement Date or provides any of them as a value that cannot be parsed into its expected type, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error identifying each offending field and SHALL NOT persist any record.
5. IF a create request provides a Line of Business identifier that does not correspond to an existing active Line of Business in the `lines_of_business` reference list, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error identifying Line of Business as invalid and SHALL NOT persist any record.
6. IF a create request provides a Customer reference that does not correspond to an existing active Customer in the Customer Master, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error identifying Customer as unresolvable and SHALL NOT persist any record.
   - **Assumption:** The Customer reference is a selection sourced from the Customer Master reference/search source (not free text) and is validated for existence against the Customer Master. Whether existence is enforced as a strict database foreign-key relationship or as presence-only validation (the reference resolves to an active Customer at submission time) is proposed for confirmation during design.
7. IF a create request provides a Product code or Scheme code that does not correspond to an active item in the configured shared Lookup catalog dropdown, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error identifying Product or Scheme as invalid and SHALL NOT persist any record.
   - **Assumption:** Product and Scheme are represented by Lookup Dropdown `Code` values. The exact Lookup Module and Type names are proposed for confirmation; the proposed module is `ApplicationProcessing` (alternative `Origination`) with Product and Scheme as the corresponding lookup Types.
8. IF a create request provides a Branch reference that does not correspond to an existing active item in the Branch Master/reference source, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error identifying Branch as invalid and SHALL NOT persist any record.
   - **Assumption:** Branch is represented by the identifier or code exposed by the existing Branch Master/reference source. The exact Branch Master endpoint and response contract are not established in this requirements document and remain confirmable during design.
9. IF a create request provides a Finance Amount that is less than or equal to 0.00 INR, or greater than 100,00,00,000.00 INR, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error identifying Finance Amount as out of range and SHALL NOT persist any record.
   - **Assumption:** A maximum Finance Amount of 100,00,00,000.00 INR (one hundred crore) is proposed as a generic upper bound for confirmation; the minimum is a positive amount.
10. IF a create request provides an IRR that is less than 0.00 percent or greater than 100.00 percent per annum, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error identifying IRR as out of range and SHALL NOT persist any record.
   - **Assumption:** An IRR range of 0 to 100 percent per annum is proposed as a generic bound for confirmation; an IRR of 0 is permitted to represent interest-free finance.
11. IF a create request provides a Tenure that is less than 1 or greater than 600, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error identifying Tenure as out of range and SHALL NOT persist any record.
   - **Assumption:** A maximum Tenure of 600 installments is proposed as a generic bound (for example, 50 years monthly) for confirmation.
12. IF a create request provides a Repayment Frequency that is not one of Monthly, Quarterly, Half-Yearly, or Annual, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error identifying Repayment Frequency as invalid and SHALL NOT persist any record.
13. IF a create request provides Processing Charges that are less than 0.00 INR, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error identifying Processing Charges as out of range and SHALL NOT persist any record.
14. IF a create request provides a Disbursement Date earlier than the current date or later than 1825 days (5 years) after the current date, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error identifying Disbursement Date as out of range and SHALL NOT persist any record.
    - **Assumption:** A Disbursement Date window of today through 1825 days ahead is proposed as a generic bound for confirmation.

### Requirement 2: Generate a Unique Application Number

**User Story:** As a Processing User, I want each application to receive a unique application number, so that every application is individually identifiable.

#### Acceptance Criteria

1. WHEN the ApplicationProcessing_Service persists a new Application, THE ApplicationProcessing_Service SHALL assign a non-empty Application Number that is distinct from the Application Number of every previously persisted Application.
2. WHEN two create requests that would persist new Applications are processed concurrently, THE ApplicationProcessing_Service SHALL assign each resulting Application a distinct Application Number and SHALL NOT persist two Applications sharing the same Application Number.
3. IF a client supplies an Application Number on a create request, THEN THE ApplicationProcessing_Service SHALL ignore the supplied value and assign a service-generated Application Number.
   - **Assumption:** Application Number is system-generated rather than user-supplied in this generic iteration; the exact format (for example, a prefixed running sequence) is proposed for confirmation during design.
4. WHEN a Processing User submits an update to an existing Application, THE ApplicationProcessing_Service SHALL retain the Application Number assigned at creation unchanged, ignoring any Application Number value present in the update request.

### Requirement 3: Generate the Amortization Schedule

**User Story:** As a Processing User, I want the system to generate an amortization schedule from the finance amount and IRR, so that I can see how the finance is repaid across installments.

> **Assumptions (for confirmation):**
> - IRR is stored and supplied as an annual percentage value (e.g., `12` means 12% per annum). The Periodic Interest Rate as a decimal fraction is therefore `IRR / 100 / periods-per-year`.
> - All monetary amounts are in INR and carry exactly 2 decimal places (paisa). The smallest representable unit is 0.01 INR.
> - Rounding to the paisa uses round-half-away-from-zero (round-half-up for non-negative values); since all amounts here are >= 0, ties at the half-paisa round up.
> - Valid inputs mean Finance Amount > 0.00 INR, Tenure is an integer >= 1, IRR >= 0, and Repayment Frequency is one of Monthly, Quarterly, Half-Yearly, Annual.

#### Acceptance Criteria

1. WHEN a Processing User requests the Amortization Schedule for an Application whose Finance Amount, IRR, Tenure, and Repayment Frequency are valid, THE ApplicationProcessing_Service SHALL generate a schedule containing exactly one Installment Line for each installment number from 1 through the Tenure, inclusive.
2. WHEN the ApplicationProcessing_Service generates the Amortization Schedule, THE ApplicationProcessing_Service SHALL compute the Periodic Interest Rate as a decimal fraction equal to the IRR percentage divided by 100 and then divided by the number of periods per year for the Repayment Frequency, where Monthly is 12, Quarterly is 4, Half-Yearly is 2, and Annual is 1.
3. WHERE the IRR is greater than 0, THE ApplicationProcessing_Service SHALL compute the EMI using the reducing-balance annuity formula `EMI = P * r * (1 + r)^n / ((1 + r)^n - 1)`, where `P` is the Finance Amount, `r` is the Periodic Interest Rate as a decimal fraction (per Criterion 2), and `n` is the Tenure, and SHALL round the resulting EMI to the nearest paisa (round-half-up) to obtain the installment amount applied to every Installment Line except the final line.
4. WHERE the IRR is equal to 0, THE ApplicationProcessing_Service SHALL set the installment amount of each non-final Installment Line to the Finance Amount divided by the Tenure rounded to the nearest paisa (round-half-up), and SHALL set the Interest Portion of every Installment Line to 0.00 INR.
5. WHEN the ApplicationProcessing_Service generates each Installment Line, THE ApplicationProcessing_Service SHALL set the Opening Balance of installment 1 to the Finance Amount, set each subsequent Installment Line's Opening Balance to the prior Installment Line's Closing Balance, compute the Interest Portion as the Opening Balance multiplied by the Periodic Interest Rate rounded to the nearest paisa (round-half-up), compute the Principal Portion as the installment amount minus the Interest Portion, and set the Closing Balance to the Opening Balance minus the Principal Portion.
6. WHEN the ApplicationProcessing_Service generates the final Installment Line (installment number equal to the Tenure), THE ApplicationProcessing_Service SHALL set the Principal Portion of that line equal to the Opening Balance of that line, set the installment amount of that line to the sum of its Principal Portion and Interest Portion (absorbing accumulated rounding differences), and set the final Closing Balance to exactly 0.00 INR.
7. THE ApplicationProcessing_Service SHALL ensure that the sum of the Principal Portions across all Installment Lines equals the Finance Amount exactly, to the paisa (0.01 INR).
8. THE ApplicationProcessing_Service SHALL ensure that every Installment Line's Opening Balance, Interest Portion, Principal Portion, and Closing Balance are greater than or equal to 0.00 INR.
9. THE ApplicationProcessing_Service SHALL ensure that each Installment Line's Closing Balance is less than or equal to its Opening Balance, and that each Installment Line's Opening Balance is less than or equal to the prior Installment Line's Opening Balance.
10. WHEN the ApplicationProcessing_Service generates the Amortization Schedule, THE ApplicationProcessing_Service SHALL return summary totals consisting of the total of all installment amounts, the total Interest Portion, and the total Principal Portion, each rounded to the paisa, where the total Principal Portion equals the Finance Amount exactly (to the paisa) and the total of all installment amounts equals the total Interest Portion plus the total Principal Portion.
11. WHEN the ApplicationProcessing_Service generates the Amortization Schedule two or more times for the same Finance Amount, IRR, Tenure, Repayment Frequency, and Disbursement Date, THE ApplicationProcessing_Service SHALL produce identical Installment Lines, identical due dates, and identical summary totals on each generation.
12. WHEN the ApplicationProcessing_Service assigns a due date to each Installment Line, THE ApplicationProcessing_Service SHALL set installment 1's due date to one Repayment Frequency period (Monthly = 1 month, Quarterly = 3 months, Half-Yearly = 6 months, Annual = 12 months) after the Disbursement Date, and set each subsequent installment's due date to one Repayment Frequency period after the prior installment's due date.
13. WHILE the Tenure is equal to 1, THE ApplicationProcessing_Service SHALL generate a single Installment Line whose Opening Balance equals the Finance Amount, whose Principal Portion equals the Finance Amount, whose Interest Portion equals the Opening Balance multiplied by the Periodic Interest Rate rounded to the nearest paisa (round-half-up), whose installment amount equals the sum of its Principal Portion and Interest Portion, and whose Closing Balance equals 0.00 INR.

### Requirement 4: Modify a Draft Application

**User Story:** As a Processing User, I want to update an application's terms while it is in Draft, so that I can correct the finance details before processing.

#### Acceptance Criteria

1. WHILE an Application is in the Draft or Submitted state, WHEN a Processing User submits an update to that Application's Line of Business, Customer, Product, Branch, Scheme, Finance Amount, IRR, Tenure, Repayment Frequency, Disbursement Date, or Processing Charges with values that satisfy the validation rules defined in Requirement 1, THE ApplicationProcessing_Service SHALL persist the change, refresh the record's UpdatedAt timestamp, leave the Application Status unchanged, and return the updated record.
   - **Assumption:** Submitted applications are editable in this generic iteration; restricting edits to Draft only is proposed for confirmation during design.
2. IF a Processing User submits an update in which any of Line of Business, Customer, Product, Branch, Scheme, Finance Amount, IRR, Tenure, Repayment Frequency, Disbursement Date, or Processing Charges violates a validation rule defined in Requirement 1, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error identifying each offending field and SHALL preserve every stored field of the existing record unchanged.
3. IF a Processing User attempts to update an Application whose identifier does not correspond to an existing Application, THEN THE ApplicationProcessing_Service SHALL return a not-found error and SHALL make no change to any Application.
4. IF a Processing User attempts to update an Application that is in the Processed state, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error indicating that a processed application cannot be modified and SHALL preserve every stored field of the existing record unchanged.
5. WHILE an Application is in the Draft or Submitted state, WHEN a Processing User submits an update whose submitted values equal the Application's current stored values, THE ApplicationProcessing_Service SHALL treat the update as a successful no-op, leave the UpdatedAt timestamp unchanged, and return the existing record.
6. WHEN a Processing User submits an update request that includes an Application Number or Application Status value, THE ApplicationProcessing_Service SHALL ignore those values and SHALL NOT alter the Application Number or Application Status in response to the update.
   - **Assumption:** Application Status changes occur only via processing (Requirement 5), not via update.

### Requirement 5: Process an Application and Persist Its Schedule

**User Story:** As a Processing User, I want to process an application so that its amortization schedule is finalized and the application is marked processed.

#### Acceptance Criteria

1. WHEN a Processing User submits a process request for an Application that is in the Draft or Submitted state and whose stored Line of Business, Customer, Product, Branch, Scheme, Finance Amount, IRR, Tenure, Repayment Frequency, and Disbursement Date satisfy the validation rules in Requirement 1, THE ApplicationProcessing_Service SHALL generate the Amortization Schedule per Requirement 3, transition the Application Status to Processed, refresh the record's UpdatedAt timestamp, and return the processed Application together with its Amortization Schedule.
2. IF a Processing User submits a process request for an Application that is already in the Processed state, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error indicating the application is already processed and SHALL make no change to the Application.
3. IF a Processing User submits a process request for an Application whose identifier does not correspond to an existing Application, THEN THE ApplicationProcessing_Service SHALL return a not-found error and SHALL make no change to any Application.
4. IF a Processing User submits a process request for an Application in the Draft or Submitted state whose stored Line of Business, Customer, Product, Branch, Scheme, or finance terms do not satisfy the validation rules in Requirement 1, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error identifying each offending field, SHALL NOT transition the Application Status, and SHALL make no change to the Application.
5. WHILE an Application is in the Processed state, WHEN a Processing User requests that Application's Amortization Schedule, THE ApplicationProcessing_Service SHALL return the same schedule that was generated at processing time.
   - **Assumption:** The processed schedule is treated as finalized and stable for the processed Application; whether a processed Application can be reopened for re-processing is out of scope for this iteration and flagged for confirmation.
6. WHILE an Application is in the Draft or Submitted state, WHEN a Processing User requests that Application's Amortization Schedule without processing it, THE ApplicationProcessing_Service SHALL generate and return a schedule per Requirement 3 for preview without transitioning the Application Status.

### Requirement 6: Consume Reference and Lookup Data for Form Selections

**User Story:** As a Processing User, I want the form's Line of Business, Customer, Branch, Product, Scheme, and classification fields populated from the platform's existing reference and lookup sources, so that I select valid values instead of typing free-form text.

#### Acceptance Criteria

1. WHEN an authenticated UI or consumer requests the Line of Business options, THE ApplicationProcessing_Service SHALL return the active Line of Business reference items (`LineOfBusinessRefResponse`) sourced from the existing active LOB reference list for selection.
2. WHEN an authenticated UI requests Customer options or performs a Customer search, THE ApplicationProcessing_Service SHALL return the matching active Customer reference items from the Customer Master reference/search source for selection.
3. WHEN an authenticated UI or consumer requests Branch options, THE ApplicationProcessing_Service SHALL return the active Branch Master/reference items from the existing Branch Master/reference source for selection.
   - **Assumption:** Application Processing consumes the existing Branch Master source generically; the exact endpoint and response contract are proposed for confirmation during design.
4. WHEN an authenticated UI or consumer requests Product lookup dropdown items for the configured Lookup Module and Product Type, THE ApplicationProcessing_Service SHALL return the active code/label items (`LookupDropdownItemResponse(Code, Label)`) from the shared Lookup dropdown API for selection.
5. WHEN an authenticated UI or consumer requests Scheme lookup dropdown items for the configured Lookup Module and Scheme Type, THE ApplicationProcessing_Service SHALL return the active code/label items (`LookupDropdownItemResponse(Code, Label)`) from the shared Lookup dropdown API for selection.
   - **Assumption:** The Lookup Module is proposed as `ApplicationProcessing` (alternative `Origination`), and Product and Scheme are proposed as the corresponding lookup Types; the exact module and type names remain confirmable assumptions.
6. WHEN an authenticated UI or consumer requests any additional lookup-backed classification dropdown for a configured Lookup Module and Type, THE ApplicationProcessing_Service SHALL return the active code/label items from the shared Lookup dropdown API for selection.
7. IF a create, update, or process request submits a Line of Business identifier, Customer reference, Branch reference, Product code, Scheme code, or other lookup code that does not correspond to an active reference item in its respective source, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error identifying the offending field and SHALL NOT persist or process any record.
   - **Note:** This ties back to the create-time validation in Requirement 1 (criteria 5 through 8) and the update/process validation in Requirements 4 and 5.
8. IF a request to read Line of Business options, Customer options, Branch Master options, Product lookup items, Scheme lookup items, or other lookup dropdown items is received without a valid JWT Bearer token, THEN THE ApplicationProcessing_Service SHALL reject the request with an unauthorized (401) response and SHALL NOT return any reference or lookup items.

### Requirement 7: Query and Search Applications

**User Story:** As a Processing User, I want to search applications by application number, Customer reference, Line of Business, Product, Branch, or Scheme, so that I can locate the correct application.

#### Acceptance Criteria

1. WHEN a Processing User requests Applications with a search term that is non-empty after trimming leading and trailing whitespace, THE ApplicationProcessing_Service SHALL return only the Applications whose Application Number or Customer reference contains the trimmed search term as a substring, matched case-insensitively, subject to the applied pagination parameters.
2. WHEN a Processing User requests Applications filtered by a Line of Business identifier, THE ApplicationProcessing_Service SHALL return only the Applications whose Line of Business reference equals the supplied Line of Business identifier, subject to the applied pagination parameters and combined with any supplied search term.
3. WHEN a Processing User requests Applications filtered by a Customer reference, THE ApplicationProcessing_Service SHALL return only the Applications whose Customer reference equals the supplied Customer reference, subject to the applied pagination parameters and combined with any supplied search term.
4. WHEN a Processing User requests Applications filtered by a Product code, THE ApplicationProcessing_Service SHALL return only the Applications whose Product lookup code equals the supplied Product code, subject to the applied pagination parameters and combined with any supplied search term or other filters.
5. WHEN a Processing User requests Applications filtered by a Branch reference, THE ApplicationProcessing_Service SHALL return only the Applications whose Branch reference equals the supplied Branch reference, subject to the applied pagination parameters and combined with any supplied search term or other filters.
6. WHEN a Processing User requests Applications filtered by a Scheme code, THE ApplicationProcessing_Service SHALL return only the Applications whose Scheme lookup code equals the supplied Scheme code, subject to the applied pagination parameters and combined with any supplied search term or other filters.
7. WHEN a Processing User requests Applications with a search term that is empty or consists only of whitespace, THE ApplicationProcessing_Service SHALL treat the request as having no search term and return the Applications subject to the applied pagination parameters and any supplied reference filters.
8. IF a Processing User requests Applications with a search term longer than 100 characters, THEN THE ApplicationProcessing_Service SHALL reject the request with a validation error indicating the search term is too long and SHALL NOT return any records.
   - **Assumption:** A maximum search-term length of 100 characters is proposed as a generic bound for confirmation.
9. WHEN a Processing User requests Applications, THE ApplicationProcessing_Service SHALL return the results as a paginated response using the platform `PaginatedResponse<T>` contract, including the page items, total count, current page number, and applied page size.
10. WHEN a Processing User requests Applications without specifying page number, THE ApplicationProcessing_Service SHALL apply a default page number of 1.
11. WHEN a Processing User requests Applications without specifying page size, THE ApplicationProcessing_Service SHALL apply a default page size of 20.
12. IF a Processing User requests a page number less than 1, THEN THE ApplicationProcessing_Service SHALL reject the request and return a validation error indicating the page number is out of range, without returning any records.
13. IF a Processing User requests a page size less than 1 or greater than 100, THEN THE ApplicationProcessing_Service SHALL reject the request and return a validation error indicating the page size is out of range, without returning any records.
14. WHEN a Processing User requests a page number beyond the last available page, THE ApplicationProcessing_Service SHALL return an empty item collection while reporting the correct total count, current page number, and applied page size.
15. WHEN returning Applications, THE ApplicationProcessing_Service SHALL order the records by CreatedAt descending, and for records sharing the same CreatedAt SHALL apply a deterministic secondary ordering by Application Number ascending.
16. IF a search request matches no Applications, THEN THE ApplicationProcessing_Service SHALL return an empty item collection with a total count of 0 and a success status.
17. WHEN a Processing User requests a single Application by its identifier and the identifier corresponds to an existing Application, THE ApplicationProcessing_Service SHALL return that Application.
18. IF a Processing User requests a single Application by an identifier that does not correspond to an existing Application, THEN THE ApplicationProcessing_Service SHALL return a not-found error.

### Requirement 8: Render the Application Processing Screen

**User Story:** As a Processing User, I want a screen that lets me enter application details and view the generated amortization schedule, so that I can process applications visually.

#### Acceptance Criteria

1. WHEN a Processing User opens the Application Processing screen, THE ApplicationProcessing_UI SHALL present input fields for Line of Business, Customer, Product, Branch, Scheme, Finance Amount, IRR, Tenure, Repayment Frequency, Disbursement Date, and Processing Charges, with Line of Business rendered as a dropdown selection populated from the active LOB reference list, Customer rendered as a searchable selection (dropdown/autocomplete) populated from the Customer reference/search source, Branch rendered as a dropdown or searchable selection populated from the active Branch Master/reference source, Product and Scheme rendered as dropdown selections populated from the shared Lookup dropdown API, Repayment Frequency rendered as a selection constrained to exactly the four fixed values Monthly, Quarterly, Half-Yearly, and Annual, and with Finance Amount and Processing Charges accepting INR values to two decimal places (paise precision). Product, Branch, and Scheme SHALL NOT be rendered as free-form text inputs.
2. WHERE the Application Processing Form presents any additional lookup-backed classification field (for example an application category or status classification), THE ApplicationProcessing_UI SHALL render that field as a dropdown selection populated from the shared Lookup dropdown API for the configured Module and Type, and SHALL NOT render it as a free-form text input.
3. WHEN the Application Processing screen loads its selection fields, THE ApplicationProcessing_UI SHALL fetch the active Line of Business, Customer, Branch, Product, Scheme, and any lookup-backed classification option lists through the shared axios instance.
4. WHEN a Processing User submits the form and every field satisfies the client-side validation rules mirroring Requirement 1 (Line of Business, Customer, Branch, Product, and Scheme selected from their active option lists; Finance Amount, IRR, Tenure, Repayment Frequency, and Disbursement Date present and non-whitespace; Finance Amount greater than 0.00 INR and not greater than 100,00,00,000.00 INR; IRR between 0.00 and 100.00 percent per annum inclusive; Tenure an integer from 1 to 600 inclusive; Repayment Frequency one of the four supported values; Processing Charges greater than or equal to 0.00 INR), THE ApplicationProcessing_UI SHALL call the ApplicationProcessing_Service through the shared axios instance.
5. WHEN the ApplicationProcessing_Service returns a success response for a submitted form, THE ApplicationProcessing_UI SHALL display the returned Application including its Application Number and Application Status.
6. IF a Processing User submits the form with any required field missing, whitespace-only, or not selected from its active option list, or any field value outside the ranges stated in criterion 4, THEN THE ApplicationProcessing_UI SHALL display a field-level validation message identifying each offending field and SHALL NOT call the ApplicationProcessing_Service.
7. WHEN the ApplicationProcessing_Service returns an Amortization Schedule, THE ApplicationProcessing_UI SHALL display the Installment Lines in a table ordered by ascending installment number, showing for each line the installment number, due date, opening balance, interest portion, principal portion, installment amount, and closing balance, together with the summary totals, with all monetary values formatted as INR to two decimal places.
8. WHILE no Amortization Schedule has been returned for the current form, THE ApplicationProcessing_UI SHALL present the schedule table in an empty state rather than displaying partial or placeholder Installment Lines.
9. WHILE a submission to the ApplicationProcessing_Service is in progress, THE ApplicationProcessing_UI SHALL prevent a further submission of the same form until the in-progress call completes or fails.
10. IF the ApplicationProcessing_Service returns an error response, THEN THE ApplicationProcessing_UI SHALL surface the error message from the response to the Processing User and SHALL retain the entered form values unchanged.
11. IF a fetch of the Line of Business, Customer, Branch, Product, Scheme, or lookup-backed classification option list fails, THEN THE ApplicationProcessing_UI SHALL surface an error message to the Processing User and SHALL NOT render the affected selection control as a silently empty, uneditable field.
12. THE ApplicationProcessing_UI SHALL render all labels, headings, and messages in English and SHALL NOT render right-to-left layout or bilingual field variants.

### Requirement 9: Authorization and Authentication Enforcement

**User Story:** As a security stakeholder, I want application processing operations restricted to authenticated, authorized users, so that only permitted personnel can create, process, or view applications.

#### Acceptance Criteria

1. IF a request to create, update, process, query, or read the schedule of an Application is received with a missing, malformed, signature-invalid, or (evaluated against the server's current UTC time allowing for the configured clock-skew tolerance) expired JWT Bearer token, THEN THE ApplicationProcessing_Service SHALL reject the request with an unauthorized (401) response, SHALL NOT create, modify, or process any stored Application, and SHALL return an error indication stating that authentication is required.
   - **Assumption:** Token expiry is evaluated against the server's current UTC time with a clock-skew tolerance (proposed as the platform default of 5 minutes) flagged for confirmation during design.
2. IF an authenticated user whose token lacks the required authorization claim attempts to create, update, process, query, or read the schedule of an Application, THEN THE ApplicationProcessing_Service SHALL reject the request with a forbidden (403) response, SHALL NOT create, modify, or process any stored Application, and SHALL return an error indication stating that authorization is required.
3. WHEN a request carrying a valid, unexpired JWT Bearer token bearing the required authorization claim invokes a create, update, process, query, or schedule-read operation, THE ApplicationProcessing_Service SHALL authorize the operation and execute it subject to the validation rules in Requirements 1 through 7.
4. WHEN the ApplicationProcessing_Service evaluates authentication and authorization for any create, update, process, query, or schedule-read request, THE ApplicationProcessing_Service SHALL enforce authentication before authorization such that a request failing both token validity and the required authorization claim is rejected with the unauthorized (401) response rather than the forbidden (403) response.
   - **Assumption:** The exact authorization claim or role governing Application Processing (for example, a SystemAdmin role or a dedicated processing role) is proposed for confirmation during design; the generic iteration requires an authenticated, authorized user.
