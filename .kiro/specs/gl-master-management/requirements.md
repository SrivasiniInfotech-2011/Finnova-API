# Requirements Document

## Introduction

The General Ledger (GL) Master Management feature (JIRA: FINNOVA-31 through FINNOVA-38, Module: SystemAdmin, Master: General Ledger) provides a centralized administrative capability for defining and governing the Finnova platform's Chart of Accounts (CoA) as a four-level hierarchy (L1 Nature → L2 → L3 → L4 Leaf Ledger). The GL Master is the authoritative source of ledger definitions that the Journal Voucher (JV) posting engine and every accounting process validate against, so ledger codes must be structurally sound, uniquely identified, strictly categorized, and governed by independent verification before they can be used for posting.

A GL Maker (Finance Controller or Accounts Administrator in the maker capacity) can create and edit GL accounts under an active, non-postable header, subject to comprehensive master validations (fixed-length numeric code, parent-prefix enforcement, per-company uniqueness, nature derivation from parent, conditional-mandatory sub-ledger and tax attributes, and closed-period checks). Every new or modified GL account passes through a Maker-Checker (4-eyes) workflow: a GL Checker, who must be a different user from the Maker, either authorizes the record (moving it to Active) or rejects it with a mandatory reason (returning it to the Maker). Once any authorized posting exists on a ledger, its structural fields become permanently read-only, and non-structural edits to an Active GL are versioned so the last authorized version continues to govern JV posting until the modification is itself authorized.

The feature also governs the GL lifecycle (freeze, deactivate, and restricted deletion under strict accounting-safety pre-conditions), enforces the configuration of mandatory system GLs per operating company before JV posting can be enabled, exposes a high-performance GL validation service consumed by the JV posting engine (FINNOVA-25), and provides search, filtering, a hierarchical CoA tree view, secure export, and an immutable audit trail. An Implementation Consultant can migrate a Chart of Accounts in bulk via an Excel/CSV upload utility with dependency-ordered dry-run validation and batch Maker-Checker authorization.

This master-data feature follows the established Lookup Master Management (FINNOVA-8) and Organization Hierarchy Master Management (FINNOVA-5) features. It follows the platform's layered CQRS conventions (ASP.NET Core Web API, MediatR, FluentValidation, EF Core + SQL Server, generic `IRepository<T>` + `RepositoryBase<T>`, record-based contracts with `.ToResponse()` mappers, `PaginatedResponse<T>`) and is hosted in the existing `Finnova.AccountsService` host (gateway cluster `accounts-cluster`, prefix `/api/accounts/**`) behind the `Finnova.ApiGateway` YARP reverse proxy, co-located with the Accounts and Transactions controllers and the FINNOVA-25 JV posting engine so that per-line JV validation (Requirement 6) is an in-process call rather than a cross-host hop. Although GL Master reuses the layered conventions established by those `Finnova.SystemAdminService` masters, it is hosted in `Finnova.AccountsService`, which must first be provisioned with the same governance stack that `Finnova.SystemAdminService` already has — JWT Bearer authentication, role-based authorization policies, the MediatR ValidationBehavior pipeline, the ExceptionHandlingMiddleware → ProblemDetails mapping, and the string-enum JSON converter. The user-facing screen is implemented in the separate Finnova-UI repository (React + TypeScript + Material UI + Vite).

This document captures the requirements derived from the JIRA tickets (FINNOVA-31 to FINNOVA-38) and their Gherkin acceptance criteria. Where the source material is silent, decisions are recorded explicitly as **Assumptions** within the relevant requirement so they can be confirmed during review.

### Dependencies and Cross-Cutting Assumptions

- **Decision (Host placement):** GL Master is hosted in the existing `Finnova.AccountsService` host, reached through the gateway `accounts-cluster` at prefix `/api/accounts/**`. GL Master is an accounting concern and is co-located with the Accounts and Transactions controllers and (per FINNOVA-25) the JV posting engine, so the GL Validation Service of Requirement 6 is an in-process dependency rather than a cross-host call. This supersedes the earlier SystemAdmin placement.
- **Dependency (Governance-stack provisioning):** The `Finnova.AccountsService` host does NOT yet configure JWT Bearer authentication, authorization policies, the MediatR ValidationBehavior pipeline, the ExceptionHandlingMiddleware, or the string-enum JSON converter (unlike `Finnova.SystemAdminService`, which does). Therefore this feature includes, as a prerequisite infrastructure dependency, porting that governance stack into `Finnova.AccountsService` — JWT Bearer authentication, authorization policies for the `GLMaker`, `GLChecker`, and `SystemAdmin` role claims and GL Viewer read access, the ValidationBehavior pipeline, the ExceptionHandlingMiddleware → ProblemDetails mapping, and the string-enum converter — mirroring the existing `Finnova.SystemAdminService` wiring. Token issuance (login) ownership remains external to this feature.
- **Dependency (API Gateway routing):** The `Finnova.ApiGateway` already routes `/api/accounts/**` to `accounts-cluster`. New GL endpoints under `/api/accounts/api/gl/**` (or the agreed path) are reached through that existing route; whether a UI alias route is needed (mirroring the `/api/ua/api/<feature>/**` aliases used for SystemAdminService masters) is confirmed during design, together with the UI axios base-URL composition.
- **Dependency (FINNOVA-25 — JV Posting engine):** Requirement 6 defines a GL Validation Service consumed by the JV posting engine (FINNOVA-25). This feature owns the validation contract and master rules; the JV posting engine owns voucher capture, balancing, and persistence. The contract boundary (request carrying voucher company, value date, branch, line currency, manual-vs-system flag, and per-line GL reference) is defined here and confirmed with the FINNOVA-25 team during design.
- **Dependency (Current GL balance):** Deactivation (Requirement 5) and the "authorized posting exists" structural-lock rule (Requirement 4) require the GL's current balance and posting existence. The authoritative balance and posting records are owned by the JV posting / ledger-balance subsystem (FINNOVA-25), not by this master. This feature reads balance and posting-existence signals through a defined query port; the ownership of that port is confirmed during design.
- **Dependency (Existing masters):** GL accounts reference the Company master (operating company), the Branch master (branch applicability list), the Currency master (GL currency), the Cost Centre / Profit Centre masters (dimension requirements), and the accounting-period / financial-calendar master (closed-period and Effective From/To checks). These masters are assumed to exist and expose read/validation access. Where a referenced master is not yet available, that gap is flagged for confirmation during design.
- **Dependency (System accounting rule / product / charge masters):** The deactivation pre-condition "not mapped in any active system accounting rules, product masters, or charge rules" (Requirement 5) depends on those masters exposing a "is this GL referenced" query. The ownership and availability of that reference-check port is flagged for confirmation during design.
- **Assumption (Multi-currency toggle):** The Realized & Unrealized FX Gain/Loss system GL requirement (Requirement 7) applies only WHERE multi-currency is enabled for the operating company. Whether multi-currency is a company-level flag owned by the Company master is flagged for confirmation during design.
- **Note (Localization):** Finnova is an India-only, English-only platform. Each GL account carries a single English display name (`GL Name`); there are no bilingual fields, no Arabic content, and no right-to-left rendering.

## Glossary

- **GL Master (General Ledger Master)**: The centralized administrative catalog defining the Finnova Chart of Accounts and the governing attributes of every General Ledger account.
- **GL Account (GL)**: A single record in the GL Master, carrying a GL Code, GL Name, Level, Parent reference, Account Nature, Normal Balance, GL Type, Postable flag, Currency, lifecycle Status, and governance/audit attributes, scoped to an operating Company.
- **Chart of Accounts (CoA)**: The full hierarchy of GL Accounts for a Company, organized across four levels.
- **Level (L1–L4)**: The depth of a GL Account in the CoA hierarchy, where L1 (Nature) is the top and L4 (Leaf Ledger) is the bottom. Only L4 leaf ledgers are postable.
- **Header GL**: A non-leaf GL Account (L1–L3) that groups child accounts and is not postable.
- **Leaf Ledger (Postable GL)**: An L4 GL Account whose Postable flag is true and against which JV lines may be posted.
- **GL Code**: A fixed-length, nine-digit numeric identifier for a GL Account, unique and non-reusable within its Company, that must begin with its Parent GL's code prefix.
- **GL Name**: The single English display name of a GL Account, unique within its Company compared case-insensitively.
- **Parent GL**: The Header GL directly above a given GL Account in the hierarchy. An L1 GL Account has no Parent GL.
- **Account Nature**: The accounting classification of a GL Account, one of Asset, Liability, Equity, Income, or Expense, derived from the Parent GL (equal to the Parent's Account Nature).
- **Normal Balance**: The side on which a GL Account normally carries its balance, derived from Account Nature: Assets and Expenses carry a Debit normal balance; Liabilities, Equity, and Income carry a Credit normal balance.
- **GL Type**: A classification of a GL Account, one of Control, Tax, or Normal (plus the system-GL designations of Requirement 9), that determines conditional-mandatory attributes.
- **Sub-ledger Type**: The sub-ledger classification attached to a GL Account; mandatory when GL Type is Control.
- **Tax Type**: The tax classification attached to a GL Account; mandatory when GL Type is Tax.
- **Postable flag**: A boolean indicating whether JV lines may be posted against the GL Account. True only for L4 leaf ledgers.
- **Allow Manual JV**: A non-structural boolean on a GL Account indicating whether manual journal vouchers may post to the account.
- **Cost Centre Mandatory / Profit Centre Mandatory**: Non-structural booleans indicating whether a JV line posting to the GL Account must carry a Cost Centre / Profit Centre dimension.
- **Branch Applicability**: The set of Branches at which the GL Account may be used for posting.
- **Reporting Line**: A non-structural attribute mapping the GL Account to a financial-statement reporting line.
- **Effective From / Effective To**: The inclusive date range during which a GL Account is valid for posting.
- **Closed Accounting Period**: An accounting period, defined in the financial-calendar master, that has been closed and into which new activity cannot be dated.
- **Status**: The lifecycle state of a GL Account, one of Draft, Pending Authorization, Active, Rejected, Pending Modification, Frozen, or Inactive.
- **Maker-Checker (4-eyes)**: A governance control requiring that a GL Account created or modified by one user (the Maker) be independently authorized by a different user (the Checker) before it takes effect.
- **GL Maker**: An authenticated user whose token carries the `GLMaker` role claim, authorized to create and edit GL Accounts and submit them for authorization.
- **GL Checker**: An authenticated user whose token carries the `GLChecker` role claim, authorized to authorize or reject GL Accounts submitted by a Maker.
- **GL Viewer**: An authenticated user authorized to search, view, export, and inspect GL Accounts and the audit trail without modification rights.
- **Authorized Posting**: A JV line that has been posted and authorized against a GL Account, as reported by the JV posting / ledger-balance subsystem.
- **Version**: An immutable snapshot of a GL Account's governing configuration; the last authorized Version remains in force for JV posting until a later modification is authorized.
- **System GL**: A GL Account designated for an automated platform function (for example Suspense, Round-off, Inter-Branch Clearing, Retained Earnings, FX Gain/Loss), configured per Company.
- **Operating Company (Company)**: A legal entity in the Company master for which a Chart of Accounts and System GL configuration are maintained.
- **JV Posting Engine**: The external subsystem (FINNOVA-25) that captures and posts journal vouchers and consumes the GL Validation Service.
- **GL Validation Service**: The capability exposed by this feature that validates each JV line against GL master rules for a given voucher value date.
- **Audit Entry**: An immutable record capturing a GL Master action (create, update, authorization, rejection, freeze, deactivation, deletion), including the affected GL identifier, the action, the acting user and role, the changed fields' old and new values, any remarks, and the timestamp.
- **Audit Trail**: The ordered, immutable collection of Audit Entries recorded for the GL Master.
- **Dry Run (Simulation)**: A bulk-upload mode that validates every row and produces a line-by-line report without committing any record.
- **EARS**: Easy Approach to Requirements Syntax; a set of structured patterns (Ubiquitous, Event-driven, State-driven, Unwanted-event, Optional-feature, Complex) used to write clear, testable requirements.
- **GL_Service**: The backend service/API responsible for GL Account management, lifecycle, validation, and retrieval.
- **GL_Admin_UI**: The React-based GL Master administrative screen used by Makers, Checkers, and Viewers (implemented in the Finnova-UI repository).

## Requirements

### Requirement 1: Create GL Account with Hierarchy and Master Validations

**User Story:** As a GL Maker, I want to create a General Ledger account under an active header with full master validations, so that ledger codes are structurally sound, uniquely identified, and correctly categorized. (FINNOVA-31)

#### Acceptance Criteria

1. WHEN a GL Maker submits a create request containing a GL Code, a GL Name, a Company, and a Parent GL reference (where Parent GL is absent only for an L1 account), THE GL_Service SHALL persist a new GL Account in Status Draft with a system-generated identifier, a Level resolved as the Parent GL's Level plus one (or L1 when no Parent GL is provided), the derived Account Nature, the derived Normal Balance, and the resolved Postable flag.
2. THE GL_Service SHALL organize GL Accounts into exactly four Levels, where L1 is the top (Nature) and L4 is the leaf, and SHALL set the Postable flag to true only for L4 leaf ledgers and false for L1, L2, and L3 header GLs.
3. IF a create request targets a Level such that the resulting GL Account would be a header GL (L1, L2, or L3) and the request sets the Postable flag to true, THEN THE GL_Service SHALL reject the request with a validation error indicating header GL accounts cannot be postable and SHALL NOT persist any record.
4. IF a create request omits GL Code, GL Name, or Company, or provides any of them as an empty or whitespace-only value, THEN THE GL_Service SHALL reject the request with a validation error identifying each missing or empty field and SHALL NOT persist any record.
5. IF a create request provides a GL Code that is not exactly nine numeric digits, THEN THE GL_Service SHALL reject the request with a validation error indicating the GL Code must be exactly nine numeric digits and SHALL NOT persist any record.
6. WHERE a create request provides a Parent GL reference, THE GL_Service SHALL require the GL Code to begin with the Parent GL's full GL Code as its leading prefix, and IF the GL Code does not begin with the Parent GL's GL Code as a leading prefix, THEN THE GL_Service SHALL reject the request with a validation error indicating the GL Code must begin with the parent prefix and SHALL NOT persist any record.
7. IF a create request provides a Parent GL reference that does not correspond to an existing GL Account in the same Company, or that corresponds to a GL Account whose Status is not Active, whose Postable flag is true, or whose Level is L4, THEN THE GL_Service SHALL reject the request with a validation error indicating the parent must be an active, non-postable header and SHALL NOT persist any record.
8. IF a create request omits a Parent GL reference and the resolved Level would not be L1, or provides a Parent GL reference and the resolved Level would be L1, THEN THE GL_Service SHALL reject the request with a validation error indicating that only L1 accounts may omit a parent and non-L1 accounts must reference a parent, and SHALL NOT persist any record.
9. WHERE a create request provides a Parent GL reference, THE GL_Service SHALL set the new GL Account's Account Nature equal to the Parent GL's Account Nature and SHALL ignore any Account Nature value supplied on the request so that nature is always derived from the parent.
10. THE GL_Service SHALL derive Normal Balance from Account Nature such that an Account Nature of Asset or Expense yields a Debit Normal Balance and an Account Nature of Liability, Equity, or Income yields a Credit Normal Balance.
11. IF a create request sets GL Type to Control and omits Sub-ledger Type, or sets GL Type to Tax and omits Tax Type, THEN THE GL_Service SHALL reject the request with a validation error identifying the missing conditional-mandatory field and SHALL NOT persist any record.
12. IF a create request omits Effective From, or provides an Effective From date that falls within a Closed Accounting Period for the Company, THEN THE GL_Service SHALL reject the request with a validation error indicating Effective From is required and cannot fall in a closed accounting period and SHALL NOT persist any record.
13. IF a create request provides an Effective To date that is earlier than the Effective From date, THEN THE GL_Service SHALL reject the request with a validation error indicating Effective To must be on or after Effective From and SHALL NOT persist any record.
    - **Assumption:** The ticket does not state the Effective From/To relationship explicitly; requiring Effective To ≥ Effective From is proposed for confirmation.
14. IF GL Name exceeds 150 characters after trimming leading and trailing whitespace, THEN THE GL_Service SHALL reject the request with a validation error identifying GL Name and SHALL NOT persist any record.
    - **Assumption:** The ticket does not specify a GL Name length bound; 150 characters is proposed for confirmation.
    - **Assumption:** The parent-prefix rule is interpreted as the child GL Code beginning with the parent's full nine-digit GL Code string; the exact per-level digit segmentation is proposed for confirmation.

### Requirement 2: Enforce GL Code and GL Name Uniqueness and Non-Reuse

**User Story:** As a GL Maker, I want the system to enforce code and name uniqueness and prevent reuse of retired codes, so that every ledger is unambiguously identified within its company. (FINNOVA-31)

#### Acceptance Criteria

1. THE GL_Service SHALL treat GL Code as unique within its Company, comparing codes exactly (character-for-character) after trimming leading and trailing whitespace, and SHALL scope every GL Code comparison to GL Accounts of the same Company only.
2. THE GL_Service SHALL treat GL Name as unique within its Company, comparing names case-insensitively after trimming leading and trailing whitespace, and SHALL scope every GL Name comparison to GL Accounts of the same Company only.
3. IF a create request specifies a GL Code that, after trimming, exactly matches the GL Code of an existing GL Account in the same Company whose Status is any value other than Inactive, THEN THE GL_Service SHALL reject the request with a validation error carrying the message "GL code must be unique" and SHALL create no new record and make no change to the existing record.
4. IF a create request specifies a GL Code that, after trimming, exactly matches the GL Code of a GL Account in the same Company whose Status is Inactive, THEN THE GL_Service SHALL reject the request with a validation error indicating the GL Code has been retired and cannot be reused, treating GL Codes as non-reusable, and SHALL create no new record and make no change to the existing record; this retired-code rejection SHALL take precedence over the uniqueness rejection in criterion 3 when a matching Inactive account exists.
5. IF a create or update request specifies a GL Name that, after trimming and case-insensitive comparison, matches the GL Name of a different existing GL Account (one whose system-generated identifier differs from the request's target) in the same Company regardless of that account's Status, THEN THE GL_Service SHALL reject the request with a validation error carrying the message "GL name must be unique" and SHALL preserve both records unchanged.
6. WHEN the GL_Service evaluates a create or update request, THE GL_Service SHALL apply required-field and format validation (Requirement 1 criteria 4, 5, 6, and 14) before the uniqueness and non-reuse checks (criteria 3, 4, and 5), such that a request with a missing, empty, whitespace-only, malformed, or over-length value is rejected on those grounds rather than on duplication.

### Requirement 3: Maker-Checker Authorization and Rejection Workflow

**User Story:** As an Accounts Administrator and Finance Controller, I want 4-eyes governance on all new and modified GL accounts, so that no ledger can be used for posting without independent verification. (FINNOVA-32)

#### Acceptance Criteria

1. WHEN a GL Maker submits a newly created GL Account for authorization, THE GL_Service SHALL set the GL Account's Status to Pending Authorization, SHALL record the Maker's identifier as the creator, and SHALL record the submission timestamp in Coordinated Universal Time (UTC).
2. WHILE a GL Account's Status is Pending Authorization or Pending Modification, THE GL_Service SHALL exclude the pending record from being usable for JV posting and SHALL present it to GL Checkers for authorization.
3. IF the user who submits an authorization (approve or reject) for a GL Account is the same user recorded as the Maker of that pending record, THEN THE GL_Service SHALL reject the authorization with an error indicating self-authorization is prohibited and SHALL leave the GL Account's Status and all attributes unchanged.
4. WHEN a GL Checker who is not the Maker approves a GL Account whose Status is Pending Authorization, THE GL_Service SHALL set the GL Account's Status to Active, SHALL record the Checker's identifier and the authorization timestamp in Coordinated Universal Time (UTC), and SHALL make the GL Account available for JV posting subject to the validation rules in Requirement 6.
5. WHEN a GL Checker who is not the Maker approves a GL Account whose Status is Pending Modification, THE GL_Service SHALL apply the pending modified configuration as the new authorized configuration, SHALL set the GL Account's Status to Active, and SHALL record the Checker's identifier and the authorization timestamp in Coordinated Universal Time (UTC).
6. IF a GL Checker submits a rejection for a GL Account without providing a rejection reason, with a rejection reason that is empty or whitespace-only, or with a rejection reason longer than 500 characters, THEN THE GL_Service SHALL reject the operation with a validation error indicating a rejection reason of 1 to 500 characters is mandatory and SHALL leave the GL Account's Status unchanged.
7. WHEN a GL Checker who is not the Maker rejects a GL Account whose Status is Pending Authorization or Pending Modification and provides a non-empty rejection reason of 1 to 500 characters, THE GL_Service SHALL set the GL Account's Status to Rejected, SHALL record the Checker's identifier, the rejection timestamp in Coordinated Universal Time (UTC), and the rejection reason, and SHALL return the record to the Maker for correction.
8. WHEN a GL Account's Status becomes Rejected, THE GL_Service SHALL permit the Maker to edit and re-submit the record, transitioning it from Rejected to Status Pending Authorization and recording the submission timestamp in Coordinated Universal Time (UTC) upon re-submission.
9. WHEN the GL_Service records any create, submission, authorization, or rejection action, THE GL_Service SHALL write an Audit Entry capturing the acting user, the acting role, the action, the affected GL identifier, any remarks or rejection reason, and the timestamp in Coordinated Universal Time (UTC), per Requirement 10.
10. IF an authorization or rejection targets a GL Account whose Status is neither Pending Authorization nor Pending Modification, THEN THE GL_Service SHALL reject the operation with an error indicating the record is not awaiting authorization and SHALL leave the GL Account's Status and all attributes unchanged.

### Requirement 4: Edit, Structural Locking, and Versioning

**User Story:** As a Finance Controller, I want strict editing controls and versioning, so that structural integrity is preserved after postings occur and unapproved modifications do not disrupt accounting. (FINNOVA-33)

#### Acceptance Criteria

1. THE GL_Service SHALL classify the fields GL Code, Parent GL, Account Nature, Normal Balance, GL Type, Postable flag, Currency, and Sub-ledger Type as structural fields, and SHALL classify Allow Manual JV, Cost Centre Mandatory, Profit Centre Mandatory, Branch Applicability, and Reporting Line as non-structural fields.
2. WHILE at least one Authorized Posting exists on a GL Account, THE GL_Service SHALL treat every structural field of that GL Account as permanently read-only, and IF an update request attempts to change the value of one or more structural fields of such a GL Account, THEN THE GL_Service SHALL reject the entire request atomically with a validation error indicating structural fields are locked once postings exist, SHALL preserve every stored field of the existing record unchanged, SHALL leave the Status unchanged, and SHALL NOT record a pending Version.
3. WHEN a GL Maker submits a change to one or more non-structural fields of a GL Account whose Status is Active and that differs from the current authorized values, THE GL_Service SHALL set the GL Account's Status to Pending Modification, SHALL retain the last authorized Version as the configuration in force, and SHALL record the proposed changes as a single pending Version associated with the Maker's identifier and the submission timestamp.
4. WHILE a GL Account's Status is Pending Modification, THE GL_Service SHALL continue to enforce the last authorized Version for all JV posting validation (Requirement 6), SHALL NOT apply any field of the pending Version to the authorized configuration until a GL Checker authorizes the modification, and IF a GL Maker submits a further change to the same GL Account while it is in Pending Modification, THEN THE GL_Service SHALL reject the request with a validation error indicating a modification is already pending authorization and SHALL leave the existing pending Version unchanged.
5. WHEN a GL Checker whose identifier differs from the Maker of the pending modification authorizes the modification, THE GL_Service SHALL apply the pending Version as the new authorized configuration, SHALL increment the authorized Version number by one, SHALL set the GL Account's Status to Active, and SHALL record the Checker's identifier and the authorization timestamp.
6. IF a GL Checker whose identifier equals the Maker of the pending modification attempts to authorize or reject that modification, THEN THE GL_Service SHALL reject the request with a validation error indicating the maker and checker must be different, SHALL leave the Status as Pending Modification, and SHALL leave the pending Version unchanged.
7. WHEN a GL Checker whose identifier differs from the Maker of the pending modification rejects the modification with a non-empty rejection reason of 1 to 500 characters, THE GL_Service SHALL discard the pending Version, SHALL restore the GL Account's Status to Active with the last authorized Version unchanged, and SHALL record the Checker's identifier, the rejection reason, and the rejection timestamp.
8. IF a GL Checker rejects a pending modification with a rejection reason that is empty or exceeds 500 characters, THEN THE GL_Service SHALL reject the request with a validation error indicating a rejection reason of 1 to 500 characters is required, SHALL leave the Status as Pending Modification, and SHALL leave the pending Version unchanged.
9. WHEN the GL_Service records an edit or a modification authorization or rejection, THE GL_Service SHALL capture a field-level difference of the old value and the new value for every changed field in the Audit Trail, per Requirement 10.
10. IF an update request targets a GL Account whose identifier does not exist in the Company, THEN THE GL_Service SHALL return a not-found error and SHALL make no change to the GL Master.
11. IF a GL Maker submits a non-structural change whose proposed values are identical to the GL Account's current authorized values, THEN THE GL_Service SHALL treat the submission as a successful no-op, SHALL leave the Status and all stored fields unchanged, and SHALL NOT record an Audit Entry.
    - **Assumption:** No-op suppression for identical modifications is proposed for a clean audit trail; confirm whether even no-op submissions should be audited.

### Requirement 5: Lifecycle Management — Freeze, Deactivate, and Restricted Delete

**User Story:** As a Finance Controller, I want to freeze, deactivate, or purge GL accounts under strict accounting-safety controls, so that historical integrity, reconciliations, and reporting remain intact. (FINNOVA-34)

#### Acceptance Criteria

1. WHEN a GL Maker requests to freeze an Active GL Account with a mandatory reason and a GL Checker who is not the Maker authorizes the freeze, THE GL_Service SHALL set the GL Account's Status to Frozen, SHALL block all new JV postings to the GL Account (per Requirement 6) within 2 seconds of the authorization, and SHALL preserve the GL Account's balances, sub-ledger ties, and financial-reporting mappings unchanged.
2. IF a freeze request is submitted without a reason, with a reason that is empty or whitespace-only, or with a reason longer than 500 characters, THEN THE GL_Service SHALL reject the request with a validation error indicating a freeze reason of 1 to 500 characters is mandatory and SHALL leave the GL Account unchanged.
3. WHEN a GL Maker requests to deactivate a GL Account, THE GL_Service SHALL permit the deactivation to proceed only WHERE all of the following pre-conditions hold: the GL Account's current balance is exactly zero; no parked, draft, or pending-authorization vouchers reference the GL Account; the GL Account has no Active child GL Accounts; and the GL Account is not mapped in any active system accounting rule, product master, or charge rule.
4. IF a deactivation request is submitted for a GL Account whose current balance is not exactly zero, THEN THE GL_Service SHALL reject the deactivation with a validation error indicating the balance must be zero and SHALL leave the GL Account's Status unchanged.
5. IF a deactivation request is submitted for a GL Account that is referenced by one or more parked, draft, or pending-authorization vouchers, THEN THE GL_Service SHALL reject the deactivation with a validation error indicating outstanding vouchers reference the GL Account and SHALL leave the GL Account's Status unchanged.
6. IF a deactivation request is submitted for a GL Account that has one or more Active child GL Accounts, THEN THE GL_Service SHALL reject the deactivation with a validation error indicating active child accounts exist and SHALL leave the GL Account and its children unchanged.
7. IF a deactivation request is submitted for a GL Account that is mapped in any active system accounting rule, product master, or charge rule, THEN THE GL_Service SHALL reject the deactivation with a validation error identifying the active mapping and SHALL leave the GL Account's Status unchanged.
8. WHEN a deactivation request satisfies all pre-conditions of criterion 3 and a GL Checker who is not the Maker authorizes it, THE GL_Service SHALL set the GL Account's Status to Inactive so that it is no longer available for new postings while remaining visible for historical reporting, and SHALL retain its GL Code as non-reusable (per Requirement 2).
9. IF a request attempts a physical deletion of a GL Account whose Status is or has ever been Active, Frozen, Pending Modification, or Inactive (that is, a GL Account that has ever been authorized), THEN THE GL_Service SHALL reject the deletion with an error indicating authorized GL accounts cannot be physically deleted and SHALL preserve the record unchanged.
10. WHEN a request to physically delete a GL Account whose Status is Draft or Rejected and which has never been authorized is submitted, THE GL_Service SHALL remove the record and SHALL record an Audit Entry for the deletion per Requirement 10.
11. WHEN the GL_Service freezes, deactivates, or deletes a GL Account, THE GL_Service SHALL record exactly one Audit Entry for the action capturing the acting user, the acting role, the reason or remarks, the affected field values, and the timestamp in UTC, per Requirement 10.
12. IF the GL Checker who authorizes a freeze or a deactivation is the same user recorded as the Maker who requested it, THEN THE GL_Service SHALL reject the authorization with a validation error indicating the maker and checker must be different and SHALL leave the GL Account's Status unchanged.
13. IF a freeze request targets a GL Account whose Status is not Active, or a deactivation request targets a GL Account whose Status is neither Active nor Frozen, THEN THE GL_Service SHALL reject the request with an error indicating the record is not in a state that permits the requested action and SHALL leave the GL Account unchanged.

### Requirement 6: GL Validation Service for JV Posting

**User Story:** As the JV Posting Engine and a Senior Accountant, I need a GL validation service that validates every journal voucher line against master rules on the voucher value date, so that invalid or non-compliant ledger postings are rejected at entry. (FINNOVA-36, contract with FINNOVA-25)

#### Acceptance Criteria

1. WHEN the JV Posting Engine submits a validation request for a journal voucher carrying an operating Company, a voucher value date, a voucher branch, a manual-or-system indicator whose value is exactly "Manual" or "System", and one to a maximum of 1000 lines each referencing a GL Account and a line currency, THE GL_Service SHALL evaluate each line against criteria 2 through 10 and SHALL return a per-line result indicating acceptance or the complete set of all applicable rejection reasons for that line.
2. IF a line references a GL Account whose Company does not match the voucher's operating Company, THEN THE GL_Service SHALL reject that line with a reason indicating the GL does not belong to the voucher company.
3. IF a line references a GL Account whose Status is not Active (that is, Pending Authorization, Pending Modification, Frozen, Rejected, Draft, or Inactive), THEN THE GL_Service SHALL reject that line with a reason indicating the GL is not active, evaluating the last authorized Version's configuration while the Status is Pending Modification.
4. IF a line references a GL Account on a voucher value date that falls outside the GL Account's Effective From and Effective To inclusive range, THEN THE GL_Service SHALL reject that line with a reason indicating the voucher value date is outside the GL effective date range.
5. IF a line references a GL Account whose Postable flag is false (a header GL), THEN THE GL_Service SHALL reject that line with a reason indicating header GL accounts cannot be posted.
6. IF the voucher's manual-or-system indicator is "Manual" and a line references a GL Account whose Allow Manual JV flag is false, THEN THE GL_Service SHALL reject that line with a reason indicating manual journal vouchers are not allowed on the GL.
7. IF a line references a GL Account whose Branch Applicability list does not include the voucher branch, THEN THE GL_Service SHALL reject that line with a reason indicating the voucher branch is not applicable to the GL.
8. IF a line references a GL Account whose Cost Centre Mandatory or Profit Centre Mandatory flag is true and the line omits the corresponding dimension, THEN THE GL_Service SHALL reject that line with a reason identifying the missing mandatory dimension.
9. IF a line's currency does not match the GL Account's master Currency, THEN THE GL_Service SHALL reject that line with a reason indicating a currency mismatch.
10. IF the voucher's manual-or-system indicator is "System" and a line references a GL Account whose GL Type is Control and the line omits a sub-ledger reference, THEN THE GL_Service SHALL reject that line with a reason indicating a sub-ledger reference is mandatory for control accounts.
11. WHEN a line satisfies all of criteria 2 through 10, THE GL_Service SHALL accept that line.
12. WHEN the GL_Service returns a validation result for a voucher, THE GL_Service SHALL report each failing line independently so that the JV Posting Engine receives, for every failing line, the complete set of all applicable rejection reasons in a single response, with the reasons for each line ordered deterministically by ascending criterion number.
13. IF a line references a GL Account that cannot be resolved (not found) in the Company, THEN THE GL_Service SHALL reject that line with a reason indicating the GL does not exist and SHALL skip criteria 2 through 10 for that line.
14. IF a validation request omits a required header attribute (Company, voucher value date, voucher branch, or the manual-or-system indicator), carries zero lines, or exceeds 1000 lines, THEN THE GL_Service SHALL reject the whole request with a validation error and SHALL return no per-line results.

### Requirement 7: Mandatory System GL Configuration

**User Story:** As a System Administrator and Finance Controller, I want to configure and enforce mandatory system-level GL accounts per operating company, so that automated balancing, settlement, and year-end procedures function correctly. (FINNOVA-35)

#### Acceptance Criteria

1. THE GL_Service SHALL require, for each operating Company, that the following System GL mappings be configured and validated — where a mapping is "validated" when the System GL type is mapped to a GL Account that belongs to the Company and whose Status is Active: a Suspense GL; a Cash/Round-off GL; Inter-Branch Clearing GLs at Head Office and branch level; a Retained Earnings / P&L Transfer GL for year-end carry forward; and, WHERE multi-currency is enabled for the Company, a Realized FX Gain/Loss GL and an Unrealized FX Gain/Loss GL.
2. WHEN a System Administrator maps a System GL for a Company, THE GL_Service SHALL require the mapped GL Account to belong to that Company and to be in Status Active, and IF the mapped GL Account does not belong to the Company or is not Active, THEN THE GL_Service SHALL reject the mapping with a validation error and SHALL NOT persist the mapping.
3. IF a request attempts to enable JV posting for a Company while one or more required System GL mappings for that Company are missing or not validated (that is, not mapped to a GL Account that belongs to the Company and whose Status is Active), THEN THE GL_Service SHALL reject the request with an error enumerating the missing or invalid System GL mappings and SHALL NOT enable JV posting for the Company.
4. WHEN all required System GL mappings for a Company are configured and validated (each mapped to a GL Account that belongs to the Company and whose Status is Active), THE GL_Service SHALL report the Company's System GL configuration as complete so that JV posting can be enabled for the Company.
5. IF a request attempts to deactivate or unmap a System GL mapping while the Company is operational (JV posting enabled), THEN THE GL_Service SHALL reject the request with an error indicating system GL mappings cannot be deactivated while operational and SHALL leave the mapping unchanged.
6. WHEN the GL_Service creates, changes, or validates a System GL mapping, THE GL_Service SHALL record an Audit Entry capturing the acting user, the action, the Company, the System GL type, the affected GL identifier, and the timestamp in UTC, per Requirement 10.
7. THE GL_Service SHALL maintain exactly one active GL mapping per System GL type per Company, and IF a request attempts to create a second active mapping for a System GL type that is already actively mapped for the Company, THEN THE GL_Service SHALL reject the request with a validation error indicating the System GL type is already mapped and SHALL leave the existing mapping unchanged.
8. WHERE multi-currency is enabled for a Company, THE GL_Service SHALL require the Realized FX Gain/Loss GL and the Unrealized FX Gain/Loss GL to be configured and validated; and WHERE multi-currency is disabled for a Company, THE GL_Service SHALL NOT require the Realized FX Gain/Loss GL or the Unrealized FX Gain/Loss GL for that Company's System GL configuration to be reported as complete.

### Requirement 8: Search, Filter, Hierarchy View, and Export

**User Story:** As an Accounts Auditor, Finance Controller, and GL Viewer, I want to search, filter, view the hierarchical Chart of Accounts tree, and export, so that I can locate and understand the ledger structure. (FINNOVA-37)

#### Acceptance Criteria

1. WHEN a user requests GL Accounts with any combination of the filters GL Code, GL Name, Account Nature, GL Type, Status, and Parent GL, THE GL_Service SHALL return only the GL Accounts matching all provided filters combined with logical AND, scoped to the requesting user's permitted Company, subject to the applied pagination parameters.
2. WHEN a user supplies a GL Code or GL Name filter value, THE GL_Service SHALL trim leading and trailing whitespace from the filter value, SHALL treat a filter value that is empty or whitespace-only after trimming as not applied, and otherwise SHALL match GL Accounts whose GL Code or GL Name contains the trimmed value as a substring, matched case-insensitively.
3. WHEN a user requests GL Accounts, THE GL_Service SHALL return the results as a paginated response using the platform `PaginatedResponse<T>` contract, including the page items, total count, current page number, and applied page size.
4. WHEN a user requests GL Accounts without specifying a page number, THE GL_Service SHALL apply a default page number of 1; and WHEN a user requests GL Accounts without specifying a page size, THE GL_Service SHALL apply a default page size of 20.
5. IF a user requests a page number less than 1, or a page size less than 1 or greater than 100, THEN THE GL_Service SHALL reject the request with a validation error indicating the pagination parameter is out of range and SHALL return no records.
6. WHEN a user requests the hierarchical Chart of Accounts tree for a Company the user is permitted to access, THE GL_Service SHALL return the GL Accounts of that Company structured across exactly four levels (L1 through L4) so that each account's children are reachable from the account, with each node carrying its GL Code, GL Name, Level, postable indicator, and Status, ordering sibling nodes by GL Code ascending.
7. WHEN a user requests an export of the current filtered result in XLSX or CSV format, THE GL_Service SHALL produce the export containing the filtered GL Accounts up to a maximum of 10,000 rows together with the export timestamp in UTC, the requesting user's identifier, and the filters applied.
8. WHILE a user holds only the GL Viewer role and lacks the GLMaker and GLChecker roles, THE GL_Service SHALL permit search, filter, tree-view, export, and audit-trail read operations and SHALL reject any create, edit, authorization, rejection, freeze, deactivation, or deletion request from that user with a forbidden (403) response.
9. IF a search or filter request matches no GL Accounts, THEN THE GL_Service SHALL return an empty item collection with a total count of 0 and a success status.
10. IF an export request specifies an export format that is neither XLSX nor CSV, or omits the export format, THEN THE GL_Service SHALL reject the request with a validation error indicating an unsupported or missing export format and SHALL produce no file.
11. IF a user requests the hierarchical Chart of Accounts tree for a Company the user is not permitted to access, THEN THE GL_Service SHALL reject the request with a forbidden (403) response and SHALL return no tree.

### Requirement 9: Bulk Chart of Accounts Upload and Migration

**User Story:** As an Implementation Consultant and Accounts Administrator, I want to upload a Chart of Accounts in bulk with a dry-run validation report, so that opening balances and new company chart setups migrate safely. (FINNOVA-38)

#### Acceptance Criteria

1. THE GL_Service SHALL accept a bulk Chart of Accounts upload in Excel (XLSX) or CSV format conforming to a standard template, and IF an uploaded file does not conform to the template structure, THEN THE GL_Service SHALL reject the upload with an error identifying the structural problem and SHALL create no GL Accounts.
2. WHEN the GL_Service processes a bulk upload in Dry Run mode, THE GL_Service SHALL validate every row against the create validations of Requirements 1 and 2 and SHALL produce a line-by-line report marking each row as success or error with the specific error reason, and SHALL NOT persist any GL Account.
3. WHEN the GL_Service validates a bulk upload, THE GL_Service SHALL validate parent GL references in dependency order so that each child row's Parent GL is validated as present (either already existing in the Company or appearing earlier in the same upload) before the child row, and IF a child row references a parent that is neither existing nor defined earlier in the upload, THEN THE GL_Service SHALL mark that row as an error indicating an invalid or out-of-order parent.
4. WHEN a Dry Run report contains one or more rows with duplicate GL Codes within the upload (compared exactly after trimming), or GL Codes (compared exactly after trimming) or GL Names (compared case-insensitively after trimming) that collide with existing GL Accounts in the Company, THE GL_Service SHALL mark each offending row as an error identifying the duplicate.
5. WHEN an Implementation Consultant submits a bulk upload for commit after a Dry Run in which every row is marked success, THE GL_Service SHALL create the GL Accounts as a single batch in Status Pending Authorization, and IF any row fails validation at commit time, THEN THE GL_Service SHALL create no GL Accounts from the batch and SHALL return the failing rows.
6. WHEN a GL Checker who is not the Maker authorizes a bulk import batch whose rows are in Status Pending Authorization, THE GL_Service SHALL set every GL Account in the batch to Status Active and SHALL record the Checker's identifier and the authorization timestamp.
7. IF a GL Checker rejects a bulk import batch with a mandatory rejection reason, THEN THE GL_Service SHALL set every GL Account in the batch to Status Rejected, SHALL record the rejection reason, and SHALL return the batch to the Maker.
8. WHEN the GL_Service commits, authorizes, or rejects a bulk batch, THE GL_Service SHALL record an Audit Entry per affected GL Account capturing the batch identifier, the acting user, the acting role, the action, and the timestamp in UTC, per Requirement 10.
9. IF an uploaded bulk Chart of Accounts file exceeds 10 MB in size or contains more than 5000 data rows, THEN THE GL_Service SHALL reject the upload with a validation error indicating the file size or row-count limit is exceeded and SHALL create no GL Accounts.
10. WHEN an Implementation Consultant submits a bulk upload for commit, THE GL_Service SHALL accept the commit only IF a Dry Run in which every row was marked success was performed for the same file or batch within the preceding 30 minutes, and IF no such successful Dry Run exists within that window, THEN THE GL_Service SHALL reject the commit with an error requiring a fresh Dry Run and SHALL create no GL Accounts.
11. IF an uploaded bulk Chart of Accounts file contains zero data rows, THEN THE GL_Service SHALL reject the upload with a validation error indicating the file contains no data rows and SHALL create no GL Accounts.

### Requirement 10: Immutable Audit Trail

**User Story:** As an Accounts Auditor, I want an immutable chronological audit log of every GL change, so that all governance actions are fully traceable. (FINNOVA-32, FINNOVA-33, FINNOVA-37)

#### Acceptance Criteria

1. WHEN the GL_Service successfully persists a create, update, submission, authorization, rejection, freeze, deactivation, or deletion of a GL Account or System GL mapping, THE GL_Service SHALL record exactly one Audit Entry (such that the count of persisted Audit Entries for that GL identifier increases by exactly one) containing the affected GL identifier, the action indicator identifying which one of the eight actions occurred, the acting user's identifier, the acting role, the old value and new value of each changed field (with old value recorded as empty for a create action and new value recorded as empty for a deletion action), any remarks or reason text up to a maximum of 1000 characters, and the timestamp of the change in Coordinated Universal Time (UTC) with millisecond precision.
2. IF a create, update, submission, authorization, rejection, freeze, deactivation, or deletion request is rejected by validation, by a uniqueness rule, by the structural-lock rule, by a lifecycle pre-condition, or by the self-authorization prohibition, THEN THE GL_Service SHALL NOT record an Audit Entry for the rejected request and SHALL leave the count of persisted Audit Entries unchanged.
3. WHEN a user requests the audit entries for a specified GL Account, THE GL_Service SHALL return the Audit Entries for that GL Account ordered by change timestamp descending, and for entries sharing an identical timestamp SHALL apply a deterministic secondary ordering by audit entry identifier descending.
4. THE GL_Service SHALL retain each Audit Entry without modifying or removing any of its recorded fields after it is recorded, and IF any request attempts to update or delete a previously recorded Audit Entry, THEN THE GL_Service SHALL reject the request without altering the stored Audit Entry and SHALL return an error indicating that audit entries are immutable.
5. IF a user requests the audit entries for a GL identifier that does not exist, THEN THE GL_Service SHALL return an empty result set and SHALL NOT return an error.

### Requirement 11: Authorization and Authentication Enforcement

**User Story:** As a security stakeholder, I want GL management, authorization, lifecycle, system-GL, bulk, and read operations restricted to the correct roles, so that only authorized personnel can view or change the ledger structure. (FINNOVA-32, FINNOVA-37)

#### Acceptance Criteria

1. IF a request to any GL Master operation is received with a missing, expired, malformed, or signature-invalid JWT Bearer token, THEN THE GL_Service SHALL reject the request with an unauthorized (401) response, SHALL make no change to any stored GL Account, and SHALL return an error indicating authentication is required.
2. IF an authenticated user whose token lacks the `GLMaker` role claim attempts to create, edit, submit, freeze, deactivate, delete, or submit a bulk upload of GL Accounts, THEN THE GL_Service SHALL reject the request with a forbidden (403) response, SHALL make no change to any stored GL Account, and SHALL return an error indicating the required role is missing.
3. IF an authenticated user whose token lacks the `GLChecker` role claim attempts to authorize or reject a GL Account, a modification, or a bulk batch, THEN THE GL_Service SHALL reject the request with a forbidden (403) response, SHALL make no change to any stored GL Account, and SHALL return an error indicating the required role is missing.
4. IF an authenticated user whose token lacks the `SystemAdmin` role claim attempts to configure, change, or enable System GL mappings or JV-posting enablement for a Company (Requirement 7), THEN THE GL_Service SHALL reject the request with a forbidden (403) response, SHALL make no change to any System GL configuration, and SHALL return an error indicating the required role is missing.
   - **Assumption:** System GL configuration and JV-posting enablement are restricted to SystemAdmin alongside Finance Controller; the exact role mapping is flagged for confirmation during design.
5. WHEN the GL_Service evaluates authentication and authorization for any request, THE GL_Service SHALL enforce authentication before authorization such that a request carrying a missing, expired, malformed, or signature-invalid token is rejected with the unauthorized (401) response rather than the forbidden (403) response.
6. IF an authenticated user whose token carries none of the recognized GL role claims (`GLMaker`, `GLChecker`, `SystemAdmin`, or GL Viewer) attempts any GL read operation, THEN THE GL_Service SHALL reject the request with a forbidden (403) response, SHALL return no GL data, and SHALL return an error indicating a GL role is required.
7. **Assumption (dependency):** THE `Finnova.AccountsService` host that exposes the GL_Service SHALL be provisioned with a JWT Bearer authentication scheme and role-based authorization policies for `GLMaker`, `GLChecker`, `SystemAdmin`, and GL Viewer read access, mirroring the scheme established in `Finnova.SystemAdminService` by FINNOVA-8 and reused by FINNOVA-5/FINNOVA-9.

### Requirement 12: GL Master Administrative UI

**User Story:** As a GL Maker, GL Checker, and GL Viewer, I want a GL Master screen with the Chart of Accounts tree, maker-checker queues, lifecycle actions, bulk upload, and audit view, so that I can manage and inspect ledgers. (FINNOVA-31 to FINNOVA-38)

#### Acceptance Criteria

1. WHEN a user opens the GL_Admin_UI, THE GL_Admin_UI SHALL present search and filter controls for GL Code, GL Name, Account Nature, GL Type, Status, and Parent GL, and SHALL render an expandable and collapsible Chart of Accounts tree of up to 4 hierarchy levels (L1–L4) with a visible postable/non-postable indicator on each node.
2. WHEN a GL Maker creates or edits a GL Account, THE GL_Admin_UI SHALL derive and display Account Nature and Normal Balance from the selected Parent GL as read-only fields, and SHALL require a non-empty Sub-ledger Type WHERE GL Type is Control and a non-empty Tax Type WHERE GL Type is Tax, and SHALL keep the submit control disabled until all required fields are non-empty.
3. IF the GL Maker attempts to submit a create or edit form while any required field is empty or fails client-side validation, THEN THE GL_Admin_UI SHALL block submission, SHALL display a validation message indicating each invalid field, and SHALL leave the entered field values unchanged.
4. WHILE a GL Account has at least one Authorized Posting, THE GL_Admin_UI SHALL render the structural fields (GL Code, Parent GL, Account Nature, Normal Balance, GL Type, Postable, Currency, Sub-ledger Type) as read-only.
5. WHEN a GL Checker opens the authorization queue, THE GL_Admin_UI SHALL present GL Accounts whose Status is Pending Authorization or Pending Modification, SHALL disable the approve and reject controls for any record whose Maker is the current user, and SHALL keep the reject submission disabled until a non-empty rejection reason of 1 to 500 characters is entered.
6. WHILE a user holds only the GL Viewer role, THE GL_Admin_UI SHALL hide or disable all create, edit, authorization, rejection, freeze, deactivation, delete, and bulk-upload controls and SHALL present search, tree-view, export, and audit-trail views only.
7. WHEN a GL Maker uploads a bulk Chart of Accounts file, THE GL_Admin_UI SHALL request a Dry Run and SHALL display a line-by-line report listing each input row with a success or error result and, for each error row, an error message, before offering a commit action.
8. WHEN a GL Maker selects the commit action after a Dry Run report, THE GL_Admin_UI SHALL submit the bulk Chart of Accounts file for commit and SHALL display the line-by-line commit result.
9. WHEN a user requests an export, THE GL_Admin_UI SHALL request the export in the user-selected XLSX or CSV format and SHALL download the returned file.
10. WHEN the GL_Admin_UI issues any request to the GL_Service, THE GL_Admin_UI SHALL include the JWT Bearer token in the Authorization header via the shared axios instance.
11. IF a request to the GL_Service fails with a validation, authorization, or conflict error, THEN THE GL_Admin_UI SHALL display the error message returned by the GL_Service and SHALL leave the affected record's on-screen contents unchanged.
    - **Assumption:** The UI follows the repo's React + hooks + MUI + shared-axios conventions (no Redux/RxJS), mirroring the Lookup and Location master screens per product-context steering.
