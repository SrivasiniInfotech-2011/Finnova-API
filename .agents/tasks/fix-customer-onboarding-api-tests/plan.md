# Implementation Plan

## Findings from static inspection

The targeted class is `Finnova.Tests/Integration/CustomerOnboardingApiTests.cs`. The test host is `CustomerOnboardingAppFactory`, which extends `SystemAdminAppFactory` and replaces only `IIndiaAddressControl` with `IndiaAddressControlTestFake`. No build or test command was run during this investigation.

The two originating interface symptoms are already represented by local working-tree fixes and must be preserved:

- `Finnova.Service/Customers/Commands/CustomerChildCommandHandler.cs` currently declares `Handle(ClearDefaultBankAccountCommand, CancellationToken)` as `async Task`, which is the return type required by `IRequestHandler<ClearDefaultBankAccountCommand>`.
- `Finnova.Tests/Infrastructure/InMemoryNationalityRepository.cs` currently implements `GetActiveByCodeAsync`, including trim, active-row filtering, case-insensitive matching, and cloning. `Finnova.Repository/Repositories/NationalityRepository.cs` and `INationalityRepository` expose the same contract.

The current Customer slice has additional, directly observable blockers:

- `Finnova.Service/Customers/CustomerPorts.cs` duplicates the Customer repository/unit-of-work interfaces that also exist in `Finnova.Repository/Interfaces/ICustomerRepository.cs`. The repository implementations implement the Repository-project interfaces, while the handlers resolve the duplicate Service-project interfaces. This leaves the handler graph unconstructable even though the repository registrations exist.
- `CreateCustomerCommandHandler`, `ModifyCustomerCommandHandler`, `QueryCustomerHandler`, and `CustomerChildCommandHandler` have no explicit Repository-interface import. They must use the single `Finnova.Repository.Interfaces` contract after the duplicate Service contract is removed.
- `Finnova.SystemAdminService/Program.cs` registers reference resolvers and repositories but does not register implementations for `IDocumentNumberGenerator`, `ICustomerAggregateMapper`, or `ICustomerProjectionMapper`. No concrete implementations of those ports exist in `Finnova.Service/Customers`, so authenticated create, modify, and query requests fail at handler activation rather than reaching the intended behavior.
- `ICustomerProjectionMapper.Project(Customer)` is synchronous, but the `Projection_resolves_current_names_without_persisting_them` test requires current names from Lookup, Nationality, and GL repositories after a master row is renamed. The projection contract and query handler must become cancellation-aware and asynchronous; otherwise the test can only return stale or absent names.
- `Customer` and its child entities expose private setters and no aggregate construction/update API. A production aggregate mapper cannot populate a create request or apply a modify request through the current public model without reflection or unsafe test-only mutation. Add focused domain factory/mutation methods and use them from the mapper.
- The Customer code-generator port has no implementation. The existing Document Number Control repository (`INumberingSchemeRepository.IssueNextAsync`) is the available generation boundary. The integration fixture must seed one global `CUSTOMER` numbering scheme whose formatted result is exactly 12 alphanumeric characters; production code must adapt that repository rather than use a GUID, request input, or an unapproved local counter.
- `CustomerUnitOfWork` calls `BeginTransactionAsync`, while `SystemAdminAppFactory` uses EF Core InMemory without configuring the provider's transaction warning. The fixture must explicitly ignore `InMemoryEventId.TransactionIgnoredWarning`; this keeps the in-memory host usable while production SQL Server retains real transactions.
- `Failed_child_validation_rolls_back_customer_and_audit` expects `400 BadRequest`, but `ExceptionHandlingMiddleware` intentionally maps `CustomerDefaultBankAccountException` to `409 Conflict` with `ERR-CUSTOMER-DEFAULT-BANK`. The test expectation is stale; change only that expected status.

## Assumptions and boundaries

- This plan covers the backend repository only because the failing class is a backend `WebApplicationFactory` integration suite; no frontend change is needed.
- The existing Lookup placeholder values are a bounded test seam, not production seed data. No bilingual, non-English, RTL, or non-India data is introduced.
- The current middleware mapping is authoritative for the default-bank status. If product explicitly requires a 400 response instead, that is a contract decision requiring a separate change to the middleware and its tests; this plan preserves current behavior.
- The planning pass did not run `dotnet build` or `dotnet test`, in accordance with the workspace workflow. Later implementation validation must provide the actual failing-test output if static findings do not explain a residual failure.
