# Design Review — Demand Processing Sample Data

## Findings

1. **HIGH — `requirements.md` R7/R8 and `design.md` Composition and startup conflict with the actual journal contract.** The enabled host keeps `ConfiguredJournalPort`, but the verified implementation throws `DemandDependencyException` on every call, both when `JournalAdapter` is empty and when it is set. `tasks.md` Task 6 registers no sample journal port and Task 10 does not replace or configure one. Therefore the March host flow cannot reach the expected rows or totals. **Fix:** add a `SampleJournalPort` that returns a deterministic `JournalCheckResult` with all four checks true, register it only in the both-flags fixture composition, and test that registration; or explicitly replace the host journal port in the factory and document that as the test-only boundary. Update the requirements/design coverage map to state which choice is used.

2. **HIGH — `requirements.md` R7 and `tasks.md` Task 9/10 cannot obtain the documented February arrears in the real March flow.** `StartDemandRunHandler` creates a run without `ProcessingCutoffReference`; `DemandProcessor` therefore passes `run:{id}:revision:{revision}` to `IPreviousDemandPort`. `SamplePreviousDemandPort` immediately returns `null` unless the reference equals `SAMPLE-DP|V1|ASOF|2026-03-31`. The expected ₹12,000 arrears for `LN-DP-0002` and ₹8,000 for `LN-DP-0004` are consequently never loaded. **Fix:** define and implement the fixture cutoff-reference flow. For example, add a sample-only cutoff reference provider/handler change that assigns `SampleDataCatalog.SnapshotReference` to the March fixture run, and test that the processor receives it; alternatively make the previous-demand adapter safely resolve and validate the processor's fallback run reference to the fixed fixture marker. Do not merely remove the equality check, because R6 requires exact marker matching.

3. **HIGH — `tasks.md` Task 10 asserts aggregate fields that the existing processor never persists.** The verified `DemandProcessor` writes current-due and arrears totals to `BillingSnapshot`, but `GenerateDemandAsync` only assigns `run.TotalDemand` and `run.TotalCharges`; it does not assign `run.CurrentDueTotal`, `run.ArrearsTotal`, `run.OdiTotal`, or `run.OtherChargesTotal`. The host test's assertions on `run.CurrentDueTotal == 48500m` and `run.ArrearsTotal == 18000m` therefore fail even after the journal and previous-demand issues are fixed, and the existing run response would expose zeros for those fields. **Fix:** either add explicit assignments for all run aggregate fields in the processor and include that change in the design/tasks, or change the acceptance and host tests to assert the persisted billing snapshot/demand rows and deliberately document that the run response does not expose those totals. The first option is required if the UI/API run summary is part of the processing test.

4. **HIGH — `requirements.md` R6, `design.md` SamplePreviousDemandPort, and `tasks.md` Task 5 do not enforce the claimed exact historical tuple.** The adapter checks some IDs and publication flags, but it does not verify the persisted `DemandRunBranchScopes` set, `DemandRun.Status`/`BillingStatus`, the stage logical scope and cutoff, the revision cutoff/dimensions, or ownership of the run, revision, stage, snapshots, and branch-scope rows. It also only checks that the returned row's branch is contained in the requested scope. A missing or extra persisted branch scope, or a tampered parent graph, can therefore still return arrears. **Fix:** load and compare the persisted branch scopes as an exact set, require completed/succeeded parent statuses, compare every LOB/frequency/period/revision/cutoff/logical-scope field, and require ownership for every fixture node used in the tuple before returning a result. Add separate SQL tests for missing, extra, unpublished, mismatched-linkage, mismatched-revision, and unowned parent/row cases.

5. **HIGH — `requirements.md` R3 and `design.md` canonical ownership claims are not implemented by `tasks.md` Task 3.** The seeder registers hashes such as `new { row.Id, row.Code, row.Name, row.IsActive }` or similarly short projections. These omit persisted business fields that the seeder writes, including several customer fields, account timestamps and optional fields, loan timestamps/KYC fields, transaction creation data, and multiple demand parent, status, display, cutoff, and linkage fields. A change to an omitted field will not change the ownership hash or manifest fingerprint, so idempotency and repair/collision diagnostics cannot have the documented meaning. **Fix:** define one canonical serializer/hash projection for each seeded entity containing every persisted fixture business field, including all foreign keys, status/type values, dates, amounts, and fixed timestamps. Explicitly list any database-generated/concurrency fields excluded from the hash, and use the canonical projection for registration, validation, and fingerprint tests.

6. **HIGH — `requirements.md` R4 and `design.md` Seeder validation promise more than `tasks.md` implements.** `SampleDataCatalog.Validate()` checks the period sequence and some location/customer/loan mappings, but it does not validate lookup-key uniqueness, receipt-key/reference uniqueness, complete application/account/customer/branch counts, receipt kind/amount invariants, transaction-field expectations, or all explicit maps. `ValidateDatabaseAsync()` checks only the location/loan counts and branch-scope count. It does not prove all foreign keys, seven historical rows/results, eight batches and statuses, snapshot/revision/stage linkage, ownership, or aggregate equations before commit. **Fix:** expand the clock-free catalog validator with an explicit allowlist for intentionally malformed receipt test vectors, then make the database validator check every documented count, FK/linkage, status/publication flag, batch/row equation, and total before the manifest and commit. Add failing preflight and rollback tests for each class of invalid catalog/database state.

7. **MEDIUM — The implementation test payload does not cover the acceptance criteria it claims to cover.** `tasks.md` Task 9 has only repeat/repair of one location, broad historical link checks, and two previous-demand negatives. It lacks the required deleted-row repair, unchanged timestamp snapshot, unowned deterministic-ID collision, natural-key collision rollback, ownership fingerprint stability, full hierarchy path, all documented receipt rejection paths through the adapter, exact previous-demand linkage/publication/ownership mutations, and migration/FK assertions. Task 8's tests do not fill all of those gaps. **Fix:** add one complete test method or clearly separated test file for each acceptance criterion, with a SQL transaction rollback assertion for both collision types and a test that invalid persisted receipts produce no allocation event. Keep all methods inside their declared class and keep every test file in a single CREATE block.

8. **MEDIUM — The silent location decision does not fully address the original “in and around Tamil Nadu” request.** The catalog contains only Tamil Nadu state/city/zone/branch rows, while the requirements and design repeatedly narrow the scope to Tamil Nadu without recording what “around” means. An implementer cannot tell whether neighboring-state branches are intentionally excluded or missing. **Fix:** add an explicit assumption such as “around Tamil Nadu means additional Tamil Nadu districts and no neighboring-state branches,” or add at least one clearly identified neighboring-state branch with the corresponding customer/account mappings and scope tests. Keep the chosen interpretation consistent in requirements, design, and catalog counts.

9. **NIT — The configuration artifact naming and authoring-boundary statements are inconsistent.** The requested deliverable names `.config`, the workspace convention names `.config.kiro`, the directory contains both, and `requirements.md` R10 says the authoring action changes only four artifacts while the actual specification directory contains five files. `design.md` and `tasks.md` also alternate between `.config.kiro` and `.config`. **Fix:** state which file is authoritative, keep the other only when required by the workspace tooling, and change the authoring-boundary/count statements so they describe the actual allowed files precisely.

## Verified Assumptions

- `requirements.md`, `design.md`, `tasks.md`, `.config`, and `.config.kiro` exist under `.kiro/specs/demand-processing-sample-data`.
- `.config` is valid JSON, contains a GUID-shaped `specId`, and contains exactly the required `workflowType` and `specType` values. The same values appear in `.config.kiro`; historical freshness cannot be proven from the working tree alone.
- The requirements document contains an Introduction, Glossary, Dependencies and Assumptions, EARS-style functional requirements, non-functional requirements, acceptance criteria, and out-of-scope material.
- The design document contains overview, repository integration, reuse/new work, a coverage map, models, contracts, components/interfaces, errors, security, testability, tradeoffs, and an implementation-ordered task list.
- The existing gateway contains the `/api/ua/api/demand-processing` alias to the Accounts cluster, so the backend-only routing reuse claim is verified in `Finnova.ApiGateway/appsettings.json`.
- The existing `DemandProcessor` passes `0m` for prior arrears, so the new previous-demand seam is real work. The existing start handler does not set a processing cutoff reference.
- The existing `ConfiguredJournalPort` always throws a dependency exception rather than returning successful journal checks.
- The existing processor persists billing snapshot totals but does not populate all corresponding `DemandRun` aggregate fields used by the query response.
- `SampleAccountSourcePort.ReadAsync` now includes `scope.BranchIds`, and the catalog's cutoff helper converts a local `Asia/Kolkata` end-of-day to UTC. Those earlier design concerns are resolved in the current documents.
- No application source, database, frontend, build, or test files were changed. The working-tree status showed only the requested specification files and review-output files as untracked, and no build or test command was run during this review.

## Unverified/Wrong Assumptions

- The claim that the enabled normal journal path can pass the March flow is wrong unless a sample journal boundary is added or the host replaces the configured port.
- The claim that the sample previous-demand adapter supplies the documented arrears in the real host flow is wrong until the run's processor-generated cutoff reference is reconciled with the fixed sample marker.
- The claim that the host test verifies the final run totals is wrong against the current processor because several run aggregate fields remain zero.
- The claim that ownership hashes represent every persisted fixture field is wrong for the projections supplied in Task 3.
- The claim that seeder validation proves all referential and aggregate invariants is unsupported by the narrow `ValidateDatabaseAsync` implementation.
- The claim that the frontend service/page is sufficient was not independently verified from `E:\Finnova\Finnova-UI\Finnova-UI` during this backend-workspace review; no frontend change is required if that claim is confirmed later.
- SQL Server availability, migration application, and runtime host behavior were not executed because the requested review explicitly prohibited builds, tests, and database operations.
